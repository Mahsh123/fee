## Objective and boundaries

Make every declared relation between tenant-owned records enforce `(tenantId, relatedId)` equality in PostgreSQL. After all constraints are installed and validated, allow Prisma relation reads and nested relation writes again, while keeping ordinary tenant predicates and scalar-reference checks in the API.

This feature adds no routes, changes no fee/payment calculations, creates no business records, and does not repair or reassign existing data. Global `Tenant` and `Permission` relations remain global. Manifest-backed polymorphic UUID references and opaque audit/outbox identifiers remain guarded by the existing tenant-scoped reference validator; this feature does not invent polymorphic foreign keys.

## Architectural issues and proposed changes

These are explicit review items, not silent implementation choices:

1. **Prisma cannot safely generate the required composite `SetNull` behavior.** Prisma 7.10 accepts `onDelete: SetNull` when a composite relation tuple includes required `tenantId`, but emits a warning and generates `ON DELETE SET NULL` for the whole source tuple. PostgreSQL then attempts to null the required tenant column as well as the optional relation ID, violating `NOT NULL` and the tenant-identity invariant. PostgreSQL can express a column-list `SET NULL` action, but Prisma's schema does not select only the optional source column. For five eligible pre-posted/draft-provenance edges, the reviewed design is to declare the composite FK with `NoAction` in Prisma and use narrowly scoped PostgreSQL `BEFORE DELETE` triggers to clear only the optional relation ID after the generated lifecycle policy approves it. Three evidence-bearing payment edges (`Payment.paymentOrder`, `GatewayTransaction.paymentOrder`, and `GatewayTransaction.settlement`) instead use `NoAction`/restricted behavior, with no detach trigger: retain PaymentOrder while any Payment/GatewayTransaction remains linked, and retain imported Settlement with `VOID`/replacement correction. This stricter behavior preserves late-webhook correlation and provider intent evidence. A prototype must validate Prisma schema/generation, deployment, generated-client behavior, five trigger paths under the runtime role, audit-chain append, no drift, and all three `NoAction` cases before these edges are enabled. If the prototype fails or architecture rejects the trigger approach, keep affected edges guarded and return the alternatives and impact for an explicit design decision.
2. **The migration account is currently also the runtime account.** Proposed deployment change: run migrations in a one-shot migration service with a dedicated migration credential; the API waits for successful completion and uses a separate DML-only runtime credential with no DDL, ownership, superuser, or constraint/trigger-disable privileges. Keep the FND-000 worker profile free of DB credentials unless a later feature requires them. This requires Compose/deployment config, role/grant setup, secret documentation, and a credential rotation step; it changes no tenant or financial rows. Other launch paths must use the same migration-before-API gate and distinct credentials.
3. **Composite FKs protect declared relation edges, not all arbitrary SQL tenant authorization.** Composite FKs reject mismatched tenant/reference tuples but do not by themselves prevent a runtime DML caller from changing a root row's `tenantId` when its references are null or remain internally consistent. The DB guarantee therefore also requires a generated `BEFORE UPDATE OF tenantId` trigger on every tenant-owned table that rejects any value change (same-value updates are allowed). API authorization remains the tenant boundary for row visibility and manifest-backed scalar/polymorphic references. Any future raw DML worker must use the same trusted tenant-validation path; runtime credentials cannot alter schema constraints or triggers. Do not describe this as general row-level security against arbitrary SQL issued by a DML credential.
4. **Several existing cascade actions can erase posted financial history.** Composite tenant keys alone preserve destructive cascades from Payment, FeeDemand, Credit, Settlement, and their financial children. The policy is now defined by a complete generated manifest below: posted or evidentiary rows are retained, corrections use lifecycle/reversal/adjustment records, and only explicitly eligible draft or pre-money graphs may be deleted. Tenant and Credit are never hard-deleted; imported Settlement, payment/provider evidence, ledger, allocation, refund, receipt, invoice, adjustment, and reconciliation history are retained under the states and conditions below. Change all financial child FK cascades (including `FeeDemandItem.demand`, `FeeDemandItemAdjustment.demandItem`, `LateFeeAccrual.demand`, `Installment.demand`, `InstallmentItem.installment`, `PaymentAllocation.payment`, `CreditAllocation.credit`, `ReceiptLine.receipt`, `InvoiceLine.invoice`, and `ReconciliationRecord.settlement`) to `Restrict`; eligible draft graph deletes are explicit ordered row deletes checked by the same guards, never FK cascades. Database guards cover direct SQL child deletes as well as parent deletes, not only the API service. The generated policy consumes both Prisma relations and the existing scalar/array/polymorphic `tenant-reference-manifest.mjs`; each reference field also declares target-delete behavior and writer locking. Generation fails if any Prisma model, relation, or manifest-backed target reference lacks a delete classification. Approved deletes/detaches append sufficient before-image audit evidence in the same transaction. This is an explicit change to existing destructive delete behavior; no existing rows are rewritten.
5. **The audit v1 chain still needs a sequenced, signed v2 cutover.** At inventory time `AuditService.record` read the last hash then inserted without a per-tenant lock, and `verifyChain` checked links without recomputing payload hashes. The legacy writer now serializes tenant appends and the verifier recomputes v1 hashes, but timestamp collisions cannot provide a durable sequence and runtime table privileges still allow direct fabrication. Proposed change: introduce an additive `AuditChainHead` row per tenant (`lastSequence`, `lastHash`, `legacySnapshotHash`), an owner-only `AuditRequestNonce` table with unique `(tenantId, requestNonce)` and transaction binding, and unique `(tenantId, chainSequence)`, `(tenantId, appendNonce)`, `hashVersion`, and canonical-payload fields on each new audit row. The migration seeds one head for every existing tenant; an `AFTER INSERT ON tenants` security-definer trigger provisions the head in the same transaction as every future tenant, so the first append never races on head creation. A single PostgreSQL append core locks the tenant head `FOR UPDATE`, increments the sequence, constructs the fixed version-2 payload from all persisted immutable audit attributes and server `recordedAt`, canonicalizes that JSON recursively (object keys sort using `COLLATE "C"`, array order is preserved, strings use JSON escaping, JSONB numeric values use PostgreSQL's normalized text, and there is no insignificant whitespace), hashes UTF-8 bytes of `fee-audit:v2\n{tenantUuid}\n{sequenceDecimal}\n{previousHashOrGENESIS}\n{canonicalPayload}`, inserts the audit row, and updates the head atomically. `AuditService.record` calls a narrow `SECURITY DEFINER` API wrapper; database triggers call the internal append core. The API wrapper accepts a fixed-schema envelope containing the canonical payload plus tenant UUID, actor ID/type, action, entity type/ID, reason, request ID/context, nonce, issued-at and expiry timestamps, and signing-key version. Its exact signature is `HMAC-SHA-256(keyForVersion, UTF8("fee-audit-api:v2\n" + canonicalEnvelope))`, where `canonicalEnvelope` uses the same specified canonical JSON encoding. The wrapper compares signed tenant/actor values with authenticated transaction-local context, atomically claims the signed request nonce in an owner-only `AuditRequestNonce` table with a unique `(tenantId, requestNonce)` and current transaction ID, and rejects any invalid signature, missing field, context mismatch, or replay. Changing the nonce, tenant, actor, action, entity, reason, request context, payload, issued-at/expiry timestamp, or signing-key version while reusing a signature must fail verification. After any relevant target/head lock waits, the wrapper checks the signed validity window using PostgreSQL wall-clock `clock_timestamp()` (never transaction-start `now()` or `CURRENT_TIMESTAMP`) and enforces a bounded maximum lifetime; request-nonce claims are retained at least through that window and are purged only after expiry plus the retry grace period and retirement of the associated verifier key. For a single signed request that produces multiple trigger before-image events, each `AuditLog.appendNonce` is a domain-separated SHA-256 of the signed request nonce plus the trigger table, stable source-row ID, and event kind; the trigger verifies that the signed nonce claim belongs to the current transaction before appending. An ordinary single API event uses the signed request nonce as its append nonce. Thus each row event has a distinct unique append nonce, while replaying the same signed envelope in a later transaction fails the request-nonce claim. The signer is versioned and rotation retains old verifier keys only for already signed/in-flight envelopes within the bounded request lifetime. For row-delete/detach trigger events, the API installs the signed transaction-local actor/context envelope binding the tenant, actor, request ID, delete/detach action, and target IDs; the trigger verifies that envelope, then the trusted database trigger itself constructs the locked before-image payload. The HMAC does not purport to sign a database-generated before image that the API did not possess. Direct SQL without a valid envelope is recorded as a database actor with no user identity; the trusted database entrypoint generates its `appendNonce` internally with `gen_random_uuid()` rather than accepting caller input. The API does not separately append an event already written by a delete/detach trigger, so each row mutation has exactly one event. The HMAC verifier key is held in an owner-only database table; the matching signer is managed as an API secret with versioned rotation. The internal core is not executable by the runtime role; the runtime role cannot direct INSERT/UPDATE/DELETE/TRUNCATE on audit rows or heads. API wrapper, tenant-head provisioning, and every lifecycle/delete/detach trigger entrypoint are `SECURITY DEFINER` functions owned by a dedicated non-login role with only the required table/function privileges, a fixed safe `search_path`, and `PUBLIC` execution revoked. Runtime has `EXECUTE` only on the signed API wrapper, not on internal core or trigger entrypoints; triggers invoke their entrypoints through DML, and each entrypoint can call the append core under its narrowly privileged owner. Tests invoke API DML under the runtime role and prove those triggers append successfully while direct invocation/core access fails. This makes a raw SQL call using only the runtime DB credential insufficient to fabricate an actor/tenant event; compromise of the trusted API process or signing secret remains inside the audit writer trust boundary. Verification orders v2 entries by `chainSequence`, checks unique contiguous sequence and head agreement, recomputes each digest from persisted canonical bytes using the same SQL canonicalizer, and confirms persisted audit columns match the committed payload. Existing rows remain byte-for-byte unchanged: migration computes a canonical digest over the complete legacy snapshot ordered by `(createdAt, id)`, stores it as the v2 epoch anchor, and recomputes that snapshot during verification. The first v2 entry chains to this anchor (or the fixed genesis value for an empty tenant). Legacy links are checked and reported separately because the old schema did not persist the exact canonical payload; the system does not claim old rows have v2 hash verification. Concurrent API/trigger append, privilege, forged/replayed-call, tamper, duplicate-event, and legacy-anchor tests are required. If this shared append contract cannot be proved, all trigger-backed detachments stay blocked.

6. **Sequence uniqueness and rendered-number format are not fully enforced.** `Sequence.scope` is nullable, so the current `(tenantId, kind, scope)` unique key allows duplicate continuous rows with `scope IS NULL`; the runtime service also reads mutable tenant settings while allocating from an existing Sequence. Proposed change: remove the existing Prisma/PostgreSQL `@@unique([tenantId, kind, scope])` key, because it both allows duplicate null scopes and blocks multiple format versions for a non-null scope. Replace it with a partial unique index on `(tenantId, kind, formatVersion) WHERE scope IS NULL` and a unique key on `(tenantId, kind, scope, formatVersion) WHERE scope IS NOT NULL`; preflight duplicates and fail without rewriting them. Revoke runtime direct Sequence `INSERT`/`UPDATE`/`DELETE` and expose a narrow `SECURITY DEFINER` reservation function called inside the consuming business transaction. It serializes first reservation, rollover, format transition, and counter advance for the tenant/kind, creates only valid initial rows, and commits number reservation atomically with the business record. Each Sequence stores an immutable snapshot of its formatting inputs, including `includeYear`, period segment, and format/settings version. A settings change creates a new Sequence format version under the same lock, seeded from the preceding version's high-water counter so changing or later reverting a prefix/format cannot reuse a rendered value. Annual reset may restart at one only when the output contains a unique period discriminator; with the current settings, `resetAnnually=true` and `includeYear=false` is an invalid combination and is rejected with a configuration error, and migration preflight reports any existing conflicting setting without changing it. Without an annual reset, period/format transitions carry the logical high-water forward. Existing tenant-scoped unique constraints on emitted business numbers remain the final collision guard. This adds only numbering metadata/indexes/function privileges and guarded `SequenceService` allocation; it adds no route and rewrites no business or financial rows. A populated migration fails on duplicate continuous sequences or invalid reset formats, and catalog plus concurrency tests prove the invariants before relation traversal is enabled.

7. **Tenant ownership must be immutable after row creation.** Composite relation FKs do not enforce this property for unreferenced rows, so the existing API-only guard is insufficient against direct runtime SQL. Generate one lightweight `BEFORE UPDATE OF tenantId` trigger for every tenant-owned table. It rejects only a changed tenant identifier, leaves row contents untouched, and is attached by the migration role; the runtime role cannot disable or replace it. The migration adds these triggers without rewriting rows. Before rollout, search all services and jobs for intentional tenant reparenting and fail the build on any remaining write path; moving data between tenants is an explicit copy with new identifiers and audit history, not an update of `tenantId`.
8. **The model inventory has grown since the original DB-001 plan.** The original implementation found 77 tenant-owned models; PAY-006 and subsequent tenant-owned audit records expanded the inventory. The current schema-derived count is 82 tenant models and 88 tenant relation edges. The DB-001 implementation must derive counts from the schema and fail closed when a model/relation is omitted; recorded generated-plan counts must be refreshed during consolidated verification.
9. **Audit cutover and extension privileges need a cross-feature contract.** The approved audit-cutover contract uses global table `public.app_schema_capabilities` keyed by `audit-chain-v2`; this implementation contract specifies its single text primary-key column as `key`. Presence of the `audit-chain-v2` row means v2 audit mode, and absence of that row (or table before its additive migration) means legacy audit mode. Bridge audit calls and runtime-grant synchronization acquire transaction-scoped shared advisory lock `(4605253, 1095058482)`, read the marker, and select the matching path. Final cutover acquires the exclusive lock, installs the v2 wrappers and marker, and revokes direct runtime AuditLog privileges in one transaction. The marker is runtime SELECT-only; all other migration-control objects remain inaccessible. Post-cutover, the runtime calls a signed append wrapper and a tenant-scoped verification wrapper that derives or validates the authenticated transaction tenant; it cannot read AuditLog, chain heads, signing keys, or nonces directly. The internal append core remains owner-only. The `POSTGRES_USER` one-shot bootstrap administrator owns both the `app_private` schema and the `pgcrypto` extension installed there, separate from the application `public` schema. Revoke schema CREATE/USAGE and extension function EXECUTE from PUBLIC and application roles; grant `app_private` USAGE and EXECUTE on only `digest(bytea,text)` and `hmac(bytea,bytea,text)` to `fee_audit_owner`. The migration role reads catalog metadata to verify the extension but receives no schema USAGE or function EXECUTE; runtime and worker receive no `app_private` privileges. The extension, schema, and member functions are explicit ACL-inventory classes and are never altered by migrations. Impact is additive marker/wrapper capability plus the reviewed extension-install ownership exception; no existing audit or business rows are rewritten. Migration deploys the bridge first, then performs the exclusive-lock cutover; rollback retains additive objects and uses the bridge binary. Incompatible pre-existing extension schema/version/ownership fails closed and requires a separately reviewed forward operation.

10. **The first composite-FK migration holds write-conflicting locks through all validations.** The current generated migration wraps 57 `ADD FOREIGN KEY ... NOT VALID`, 57 `VALIDATE CONSTRAINT`, and 57 legacy-FK drops in one transaction. PostgreSQL's initial FK-add locks on referencing and referenced tables conflict with ordinary writes and remain held until commit, so the full set of validation scans can extend the write pause. Proposed migration plan amendment: if this migration is confirmed unapplied, replace it with three separately tracked post-index migrations: (a) add all composite FKs as `NOT VALID` in a short transaction, (b) validate them in a separate transaction, and (c) drop legacy ID-only FKs only after every composite FK is validated. Keep relation traversal fail-closed until all three stages and the broader DB-001 gate pass. Partial state is safe: once added, each `NOT VALID` FK enforces new writes; if validation fails, retain both old and new constraints, repair data through an approved forward procedure, resolve/retry the failed validation migration, and do not enable relation access. Give every phase an explicit transaction and bounded lock/statement timeouts. If this migration has already been applied in any shared or production environment, do not rewrite its recorded history; use the documented write-pause rehearsal or a separately reviewed forward remediation. This changes migration boundaries and failure/recovery behavior, adds migration history entries, and changes no business or financial rows.

   Recovery is catalog-driven. Phase A is fully applied only when all 57 exact composite constraints exist with expected names, columns, targets, and actions, are unvalidated, and all 57 legacy ID-only constraints remain; it is unapplied only when no composite constraint exists and all 57 legacy constraints remain. Phase B is fully applied only when those same 57 composite constraints are validated and all legacy constraints remain; it is rolled back only when all 57 expected composite constraints exist unvalidated and all 57 legacy constraints remain. Phase C is fully applied only when all 57 exact composite constraints remain validated and no legacy ID-only constraints remain; it is rolled back only when all 57 composite constraints remain validated and all 57 legacy constraints remain. For an ambiguous commit, query and record this full catalog state before using Prisma's `migrate resolve --applied` or `--rolled-back`; never infer state from the process exit code alone. Any mixed, duplicate, differently-actioned, or otherwise unexpected state stops for manual review. Phase C verifies the complete expected composite-FK inventory before dropping any legacy constraint, and all drops commit atomically. Test restart after A, injected B validation failure plus approved data repair/retry through the staged migration orchestrator after Prisma resolution, ambiguous commit resolution in every phase, and writers during all phases. Architecture review conditionally accepts the phase-splitting design; PostgreSQL 17 rehearsal and implementation reviews remain required. This amendment does not complete DB-001.

## Database changes

- Add a schema-level unique key on `(tenantId, id)` to each tenant-owned target model.
- Change each relation from a tenant-owned source to a tenant-owned target to use `fields: [tenantId, relatedId]` and `references: [tenantId, id]`. Relations to `Tenant` or global `Permission` remain unchanged.
- Keep the tenant's direct `tenantId -> Tenant.id` foreign key on every tenant-owned table.
- Change every financial-evidence child FK from cascading delete to `Restrict`, including all listed fee-demand, allocation, installment, receipt, invoice, and reconciliation children. Eligible draft graph deletes explicitly delete rows in dependency order after each row passes the policy guard; no FK cascade can erase a child. Generate API and database lifecycle checks from one checked-in delete-policy manifest plus `scripts/tenant-reference-manifest.mjs`. Require coverage for all Prisma models, relation actions, and scalar/array/polymorphic reference fields so newly added edges cannot silently inherit an unsafe action. Retain imported settlements with an additive `VOID` status and reason/timestamp/actor fields; set both `GatewayTransaction.settlement` and `GatewayTransaction.paymentOrder`, plus `Payment.paymentOrder`, to `NoAction` so provider evidence and late-webhook correlation remain attached to their original intents. A PaymentOrder with any linked Payment or GatewayTransaction is retained/cancelled/expired instead of hard-deleted.
- Runtime API deletes use the approved delete policy; allowed draft-only deletes and SetNull detachments write the hash-chained audit row in the same transaction. Database guards reject raw SQL deletes that would erase issued, posted, allocated, reconciled, or otherwise used financial history. Tenant hard delete is disabled in favor of archival.
- Add an `AuditChainHead` row per tenant, an owner-only versioned `AuditSigningKey` verifier table, an owner-only `AuditRequestNonce` replay table, and unique `(tenantId, chainSequence)`/`(tenantId, appendNonce)`, canonical-payload, and hash-version fields for v2 `AuditLog` entries. Install PostgreSQL `pgcrypto` into `app_private` as the one-shot bootstrap administrator and fail deployment if the configured server cannot provide its SHA-256/HMAC functions at the required version/schema/owner. Only `fee_audit_owner` receives schema USAGE and EXECUTE on the required `digest(bytea,text)` and `hmac(bytea,bytea,text)` functions; PUBLIC, migration, runtime, and worker receive no extension function EXECUTE, and runtime/worker receive no schema USAGE. One PostgreSQL canonicalization/hash/append core is shared by the API wrapper and database triggers, locks the head `FOR UPDATE`, and appends/advances the head in one transaction. The API wrapper verifies the exact canonical HMAC envelope and one-time nonce; the verifier recomputes every v2 digest, confirms sequence/head integrity and committed-column equality, and recomputes a deterministic legacy-snapshot anchor without rewriting legacy rows. The global `public.app_schema_capabilities` marker uses key `audit-chain-v2`; bridge calls and grant synchronization share advisory lock `(4605253, 1095058482)`, while cutover takes its exclusive form to commit the marker and revoke direct AuditLog grants atomically. Runtime has marker SELECT only, and post-cutover audit append/tenant-scoped verification EXECUTE only. Runtime credentials cannot directly select, insert, update, delete, or truncate audit/head/signing-key/request-nonce rows. The `SECURITY DEFINER` ownership, fixed search path, HMAC validation, trigger-entrypoint privileges, and `EXECUTE` grant boundary are part of the migration contract.
- Build missing target unique indexes and child-side FK indexes in staged `CREATE INDEX CONCURRENTLY` steps outside transactions, reuse equivalent existing indexes, detect and safely clean up invalid indexes, then attach target unique constraints.

## Domain and financial rules

- A tenant-owned record may relate only to another record in the same tenant.
- Parent/child and join-table relations remain tenant-local, including self-relations such as `AcademicUnit.parent`.
- Deleting a tenant-owned target must not clear or change the source row's `tenantId`.
- Posted/issued/reconciled financial evidence is immutable. Corrections use the existing void, reversal, adjustment, refund, or credit lifecycle; a delete is never used to correct money or erase evidence.
- Financial delete guards apply to API deletes and direct SQL using the runtime role. Draft-only rows may be deleted only when the state and complete downstream graph satisfy the table below. Disallowed attempts leave every row and field unchanged.
- Any allowed SetNull detach records the source and target IDs, relation name, prior/current relation values, actor/context when available, and timestamp in the tenant hash-chained audit log inside the same transaction. Amounts, statuses, lifecycle timestamps, receipts, refunds, ledger entries, allocations, and reconciliation records are unchanged.
- Every permitted hard delete writes a full before-image for each deleted row and detached source/target into the append-only audit chain in the same transaction. For a draft graph delete, the ordered row events preserve every deleted row's primary/tenant IDs, lifecycle state, money values, calculation/provenance fields, timestamps, and relation edges; fields marked secret are redacted by the manifest. This snapshot supplements, and never replaces, rows the matrix requires to remain in ledger or evidence tables.
- Tenant hard deletion is blocked; tenant offboarding uses `ARCHIVED`.

Each relation and nonrelational reference entry declares allowed target-delete predicate, source-field write lock, downstream graph predicate, API action, generated DB guard, FK action, and audit event. Generation/parity tests fail for an unclassified model, relation, reference field, discriminator value, or deletion path. `Sequence` has the `NUMBERING_STATE` classification: once a number is reserved, its value and period history are never reset or hard-deleted. ### Delete and lifecycle concurrency contract

Every lifecycle operation that can race with a delete/detach (issue/cancel demand, create an allocation or credit allocation, capture/confirm payment, refund, write ledger, close settlement, reconcile, void invoice/receipt/credit, reserve a document number, or start an annual numbering period) runs in one database transaction and locks its canonical financial/numbering root row before checking state or graph predicates. Generated database guards take the same root lock before evaluating a delete/detach/reset. Child insert/update triggers lock the referenced root before adding or changing evidence, so an eligible-empty-graph check cannot race with a new child. Multi-root operations acquire locks in a single manifest-defined order `(tenantId, modelOrdinal, id)`; then child rows, then the per-tenant audit head. A period rollover creates the new scoped Sequence row atomically and cannot alter a previous period's `nextValue`. State check and mutation commit atomically. Serialization/deadlock conflicts retry only through the existing bounded transaction retry policy; exhaustion returns a retryable domain error and writes no partial financial or audit state. Direct child deletes of immutable evidence are rejected independently of locks.

Concurrency verification is generated from every manifest delete predicate and reference writer, with barrier pairs for: AcademicUnit delete vs soft-delete/restore/activate, membership/primary-unit/policy/assignment/structure/admission reference creation; AdmissionApplication delete vs submit, Admission conversion, demand/payment creation; FeeAssignment delete vs draft-demand generation; FeeDemand/item delete vs issue, invoice attach/issue, payment/credit allocation, scalar/array reference writes; Payment delete vs external dispatch, capture, lost response, late webhook, refund, reversal-reference creation; PaymentOrder delete vs new Payment/GatewayTransaction, late webhook, and IdempotencyKey create/replay/expiry; Credit.payment detach vs CreditAllocation/state transition; Invoice.demand detach vs invoice issue/attach/payment; Settlement VOID/correction vs reconciliation and late provider event. The winner may complete only if its locked predicate remains true; the loser retries or is rejected. Full graph snapshots and recomputed audit verification prove there is no lost allocation, erased event, dangling live reference, duplicate audit sequence, or partially committed detach.

## Security and tenant implications

- PostgreSQL constraints defend declared relation-edge integrity; tenant authorization, row visibility, and manifest-backed scalar-reference validation remain in the trusted API/runtime layer.
- Runtime DB credentials cannot own tables, run DDL, or disable triggers/constraints; only the one-shot migration service receives the migration role.
- Relation reads become safe only after the database validates every relevant FK; deployment must never start code that permits relation traversal before migration success.
- A mismatch, orphan, missing composite index, or unvalidated constraint blocks relation enablement and rollout.
