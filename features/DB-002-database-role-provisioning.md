> **Current deployment note (2026-10-05):** The historical bundled-PostgreSQL Compose
> flow described below is no longer used by the application stacks. Both Compose files
> use Neon; Compose does not create PostgreSQL or provision roles. The role provisioning

The new schema grants and synchronizer assertions have not run against PostgreSQL and remain unverified.

Initial verifier provisioning is assembled but has not been exercised; key retirement, grace-period cleanup, and an audited rotation procedure remain open.

## Source requirements

- `fee_collection_saas_architecture.md`, §7: tenant-owned data uses the shared PostgreSQL database and each request/job must use authenticated tenant context.
- `fee_collection_saas_architecture.md`, §51: establish the PostgreSQL migration system before domain features.
- `fee_collection_saas_architecture.md`, §55: include PostgreSQL backups, point-in-time recovery where supported, encrypted backups, object-storage versioning, restore testing, migration rollback, and incident runbooks.
- DB-001, Architectural issue 2 and database changes: migrations use a dedicated role; API uses a separate DML-only role; runtime credentials cannot own objects, alter DDL, or bypass database guards.
- Historical FND-002 baseline: the bundled Compose target was PostgreSQL 17 at `postgres:5432`, schema `public`; current Neon Compose behavior is recorded in [ADR 20261005](../docs/architecture/decisions/20261005-neon-compose-runtime.md).

## Objective and boundaries

Create a repeatable first-run/rotation path for managed or self-hosted PostgreSQL. Provisioning runs as an explicit operator action before migration. It creates or rotates configured migration, runtime, and read-only backup login roles plus non-login function-owner roles, applies least-privilege database/schema grants, and establishes an exhaustive operation-level ACL after migrations. Application API and worker processes never receive the bootstrap credential; the backup process receives only its restricted backup credential. This slice adds no HTTP routes, tenant records, fee behavior, or financial mutations.

This does not claim row-level security: SQL privileges are a database capability boundary; authenticated tenant scoping remains enforced in the API. Financial tables stay inaccessible to direct runtime DML until their DB-001 invariant guards or narrow database functions are implemented and reviewed.

## Proposed implementation

- Add one-shot `database-roles` and `database-roles-finalize` Compose services, ordered `postgres healthy → database-roles successful → migration successful → database-roles-finalize successful → API startup`. The bootstrap temporarily grants database-level CREATE only to the migration role because the immutable Prisma baseline contains `CREATE SCHEMA IF NOT EXISTS public`; the finalizer revokes it and verifies that migration, runtime, backup, and PUBLIC do not retain it. API, worker, and backup start only after finalization. Bootstrap and finalizer receive the administrator credential; only bootstrap receives the migration/runtime/backup passwords. The migration service receives only its dedicated migration login. Bind the backup target to the same validated host, port, database, and `public` schema used by API and migration. Production backup can run after finalization even when API startup fails.
- Serialize bootstrap in one database transaction under a dedicated advisory lock. Before mutation, validate that administrator, migration, runtime, and backup role names/passwords are pairwise distinct; validate the resolved database target; and inspect existing role attributes and memberships. Existing unsafe roles fail closed; provisioning never silently downgrades an administrator or removes unexpected memberships. Concurrent attempts and partial failures must leave either the complete old role/grant state or the complete new state.
- Treat `POSTGRES_USER` bootstrap administration and the migration login as trusted deployment principals: their DDL/ownership capabilities mean this design cannot technically prevent a malicious or compromised administrator/migration from rewriting history. Application requests, APIs, and workers never receive these credentials. Protect this boundary with access control, immutable/checksum-verified forward-only migrations, reviewed migration diffs, backups, and complete before/after audit and posted-financial snapshots on populated-database upgrades. Report this as an operational trust boundary, not as a privilege-denied guarantee.
- Create non-login, non-admin function-owner roles for audit, lifecycle, and numbering code. Only the migration role may `SET ROLE` to these explicitly named owners when a reviewed migration assigns a security-definer function; runtime has no membership. Each migration-to-owner membership is explicitly `INHERIT FALSE, SET TRUE` with no ADMIN OPTION: migration may assume an owner only inside a reviewed migration but has none of its effective privileges before `SET ROLE`. Bootstrap verifies membership options and rejects unexpected membership. Owner roles receive only the exact privileges declared by their reviewed object/column/function manifest. The migration login's steady-state database privileges are CONNECT only, with `public` USAGE/CREATE. Database CREATE is a temporary, startup-gated deployment exception required by the checksum-verified initial migration; the separate administrator-only finalizer removes it before application startup. See [the recorded architectural decision](../docs/architecture/decisions/20261005-prisma-bootstrap-schema-privilege.md).
- Provision function-owner roles with no default application-data privileges. A reviewed migration and ACL manifest grants only these operation masks when it creates the corresponding guarded feature: `fee_audit_owner` gets `AuditLog SELECT/INSERT` only (never UPDATE/DELETE/TRUNCATE), `AuditChainHead SELECT/INSERT` plus column-scoped UPDATE only for `lastSequence` and `lastHash`, `AuditSigningKey SELECT` only, and `AuditRequestNonce SELECT/INSERT` plus DELETE only for a reviewed expired-nonce cleanup path; `fee_lifecycle_owner` gets column-scoped SELECT for the generated lifecycle predicates and column-scoped UPDATE only for `AcademicUnit.parentId`, `Admission.applicationId`, `FeeDemand.feeAssignmentId`, `Credit.paymentId`, and `Invoice.demandId`, with no INSERT/DELETE/TRUNCATE; `fee_numbering_owner` gets column-scoped SELECT on `Sequence` (`id`, `tenantId`, `kind`, `formatVersion`, `scope`, `nextValue`), column-scoped INSERT only for reservation snapshots/counters, column-scoped UPDATE only for `nextValue` and `updatedAt`, and column-scoped SELECT only for the `TenantNumberingSettings` inputs captured by a reservation. Numbering format/scope fields in an allocated `Sequence` are immutable. Runtime gets EXECUTE only on the two tenant-bound numbering functions and never direct `Sequence` access. All remaining function/table/column/function-EXECUTE privileges are enumerated per migration; no schema-wide DML grant is allowed. These masks apply only after the corresponding reviewed DB-001 migration exists.
- Runtime receives CONNECT and `public` USAGE only as its base ACL. Revoke PUBLIC CONNECT/TEMP and public-schema CREATE on this dedicated application database/schema, then grant CONNECT only to approved roles. Verify effective rights including PUBLIC grants, column privileges, role memberships, default ACLs, and function EXECUTE. The runtime role must not create/own objects or use TRIGGER, TRUNCATE, REFERENCES, sequence `setval`, or any unclassified application function.
- `fee_backup` is a login role for the dedicated bundled PostgreSQL cluster with read-only privileges required for `pg_dump`: target-database CONNECT, `public` USAGE, SELECT on every public table/view/materialized view included in the dump (including an explicit backup-only SELECT exception for otherwise owner-only `AuditSigningKey` and `AuditRequestNonce`), and SELECT on every public sequence. It receives no DML, sequence USAGE/UPDATE, schema CREATE, `app_private` access, or application-function EXECUTE. Since PostgreSQL roles are cluster-wide and default PUBLIC CONNECT can span databases, bootstrap revokes PUBLIC CONNECT on every non-target database in this dedicated cluster, revokes any direct CONNECT grant to `fee_backup` on those databases, and grants target CONNECT only to approved roles; this policy must not run against a shared external cluster. The backup target is validated against the same shared target as API/migration, and catalog checks assert effective `has_database_privilege(..., 'CONNECT')` is false for `fee_backup` on every non-target database. An integration test proves connection to a second database is denied. The catalog manifest grants this backup read set exactly; unknown objects fail closed and backup remains gated until a successful sync. The backup password and dump are sensitive: only the backup job receives its role password, its connection is target-bound, and `pg_dump` output is streamed directly through `age` using the configured public recipient before it reaches persistent storage. No plaintext dump is written to the backup volume. The corresponding private identity remains outside the application deployment; encrypted dumps are not production-ready until restore tests pass.
- Replace broad table DML with a checked-in per-object ACL manifest. It must classify every Prisma model and every physical table/function/sequence created by SQL migrations, including implicit join and raw-SQL objects. New or unexpected catalog objects fail closed. The current manifest grants auth paths only their required reads/writes, and enables the reviewed TEN-001 settings surface: `TenantBranding` and `TenantNumberingSettings` SELECT/INSERT plus field-specific UPDATE, with no DELETE; numbering sequence data remains accessible only through its approved reservation RPC. Auth grants include `Tenant`, `Role`, `Permission`, `UserRole`, and `RolePermission` SELECT; `User` SELECT plus column-scoped UPDATE of `lastLoginAt`, `failedLoginCount`, `lockedUntil`, and `updatedAt` (Prisma's `@updatedAt` behavior adds `updatedAt` to these login-state writes); `RefreshToken` SELECT/INSERT plus column-scoped UPDATE of `revokedAt`; a temporary `AuditLog` SELECT/INSERT exception for the current legacy AuditService; and `app_schema_capabilities` SELECT so the bridge can choose the correct audit path. Before cutover, this AuditLog exception trusts the application process and does not prevent a holder of runtime credentials from fabricating legacy audit rows; it is not a non-forgeability guarantee. The exclusive-lock cutover revokes direct AuditLog SELECT/INSERT and post-cutover runtime audit access is wrapper-only. All other data tables are denied by default until their feature and database invariants are reviewed. Deny `_prisma_migrations`, `SchemaIndexBuild`, `Sequence`, and all direct financial table DML. The marker is the sole migration-control exception: runtime may only SELECT it; `_prisma_migrations`, `SchemaIndexBuild`, and every other migration/control object remain inaccessible. The generated physical-table inventory must exactly match the PostgreSQL catalog plus individually classified migration-control/extension objects; an implicit join or raw-SQL table cannot be silently omitted. AuditLog never receives UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER; the capability marker never receives runtime INSERT/UPDATE/DELETE.
- `SequenceService` now calls the transaction-bound `SECURITY DEFINER` reservation function through a narrow transaction RPC; the RPC also establishes and checks the active tenant context. Configuration edits and reservations take the same tenant lock. Runtime receives EXECUTE only on the reservation and configuration-lock functions, not the backing `Sequence` table or function-owner role. Migration `20261003000500_sequence_reservation` is implemented but still awaits the consolidated PostgreSQL integration pass and independent reviews before the feature is complete.
- **Approved DB-001 audit-cutover contract:** the global marker is `public.app_schema_capabilities`, key `audit-chain-v2`; no row means legacy mode. The two-integer transaction advisory key `(4605253, 1095058482)` is reserved for this cutover. Bridge audit calls and runtime-grant synchronization take the shared transaction lock, read the marker, and choose/apply grants in that transaction; `db:audit-cutover` takes the exclusive transaction lock, verifies and anchors all tenant histories, installs the v2 marker, and revokes direct runtime access to audit data atomically. Before cutover, AuditLog direct access is SELECT/INSERT only. After cutover, runtime has no direct audit-table/head/key/nonce access and receives EXECUTE only on signed append, tenant-scoped verification, and tenant-scoped list/detail wrappers owned by `fee_audit_owner`; the internal append core remains inaccessible. The marker-selected ACL path and operator command are assembled but await PostgreSQL integration and consolidated review. No existing audit row rewrite is intended.
- **Approved private pgcrypto contract:** PostgreSQL 17's trusted `pgcrypto` extension still requires the installing role to have database CREATE ([PostgreSQL 17 `CREATE EXTENSION`](https://www.postgresql.org/docs/17/sql-createextension.html)). The role configured by `POSTGRES_USER` is the one-shot bootstrap administrator; it owns both the private `app_private` schema and `pgcrypto` installed there before migrations. Bootstrap verifies the expected extension version, schema, owner, and extension-member objects and refuses to relocate/re-own an existing installation. Revoke schema CREATE/USAGE and extension-function EXECUTE from `PUBLIC` and all login roles, then grant `USAGE, CREATE` on `app_private` to the non-login `fee_audit_owner` so reviewed security-definer routines can be created under their required owner; grant `USAGE, CREATE` to `fee_numbering_owner` for its narrow routines. Grant EXECUTE only to `fee_audit_owner` on `app_private.digest(bytea,text)` and `app_private.hmac(bytea,bytea,text)`. `fee_migrator` has no effective `app_private` USAGE or function EXECUTE before `SET ROLE`; its membership to the function owners is `INHERIT FALSE, SET TRUE` with no ADMIN OPTION. The API runtime role gets `USAGE` only because it calls the two narrow numbering functions; it receives no `CREATE` and no digest/HMAC execution. Backup and worker receive no private-schema usage. Notification outbox/reminder processing now runs in the API under tenant context; the standalone worker is delivery-only and receives no database credential. Consolidated review must verify the operation-level API grants and that the worker remains database-free. Bootstrap verifies the exact schema grants. Migration verification reads catalog metadata. The ACL inventory classifies the extension and its functions as bootstrap-owned extension objects, not migration-managed business objects. No migration may alter extension-owned objects. Impact: extension installation ownership moves from the migration role to the bootstrap administrator, with no business-data change. A mismatched installation requires a separate reviewed forward operation. `public` remains the application schema used in FND-002. The audit-owner `CREATE` adjustment and rollback are recorded in [ADR 20261003](../docs/architecture/decisions/20261003-audit-owner-schema-create.md).
- Grant synchronization runs only in the staged migration path, under the shared audit-cutover lock and within one transaction; it verifies exact catalog privileges after applying them. It repairs known ACL drift only on manifest-listed objects (including revoking extra grants before reapplying exact allowed privileges); startup proceeds only after repair and re-verification succeed. Unknown objects, ownership drift, unsafe memberships, unclassified/default-ACL drift, or known drift that cannot be repaired fail without mutation and block startup. It checks `pg_largeobject_metadata` before any ACL mutation and fails closed if the inventory is unavailable or contains a large object. Post-index migrations may add constraints/triggers but may not add application data tables; any new application model goes through the pre-index stage and an explicit ACL-manifest review.
- Keep login role names/passwords configurable. Configured bootstrap and login passwords currently accept printable ASCII only so PostgreSQL/libpq SCRAM processing has no normalization ambiguity. Do not print database URLs, passwords, or secret-bearing connection errors. Password changes update only their configured role and are rotated through the same one-shot sequence during a maintenance window: stop/drain API instances, migration, and the long-running backup job before changing role passwords/secrets; then provision, migrate/grant-sync, and start the API and backup with their new credentials. Existing PostgreSQL sessions remain authenticated after password alteration, but cannot safely reconnect with the old password; the procedure therefore does not depend on old pools surviving. If provisioning/migration fails before API health, restore the old role passwords and deployment secrets using the bootstrap administrator, verify role state, then retry or restore service. Tests cover old-session behavior, failed rotation rollback, and successful retry.
- Existing databases are not silently reassigned. Preflight inventories all migration-managed object classes whose owner prevents migration (schemas, tables/partitioned tables, views, sequences, types/domains, and functions/procedures); on mismatch, provisioning fails without changing ownership or data. Any object-scoped adoption is a separate reviewed operation.

## Acceptance criteria

- [ ] Development and production Compose order role provisioning before migration and privilege finalization. API, platform seed, and backup wait for finalization; backup does not wait for API health and remains available if API startup fails.
- [ ] Only the one-shot bootstrap and finalizer receive the admin credential; only bootstrap receives migration/runtime/backup role passwords. Migration receives only its own credential and runtime/backup role names needed for guards; API receives only its runtime credential; backup receives only its read-only backup credential; worker receives neither.
- [ ] Provisioning is idempotent for matching roles, supports explicit password rotation, rejects role aliasing and unsafe existing attributes/memberships, and does not log secrets.
- [ ] Migration deploys from a clean PostgreSQL 17 database as the configured non-admin role. During migration it has CONNECT, schema-level CREATE, and the temporary database CREATE needed by the immutable Prisma baseline; finalization removes database CREATE before API, worker, seed, or backup startup. Runtime cannot create database/schema objects, own application objects, assume the migration role, or alter constraints/triggers.
- [ ] Runtime and backup ACL generation covers every Prisma model and every application catalog object exactly once; new/unexpected tables, implicit joins, sequences, and functions fail closed. Tests compare table/column DML, sequence USAGE/SELECT/UPDATE, function EXECUTE, PUBLIC grants, role membership and membership options, default ACL, database CONNECT/TEMP, and schema privileges against the reviewed manifest. Under actual PostgreSQL roles, migration can `SET ROLE` to each approved owner but has no inherited owner privileges before doing so; runtime and backup cannot assume any owner. Backup can read every dump-required table/view/sequence but cannot mutate rows, create objects, change sequence values, or invoke application functions. Its SELECT exception for `AuditSigningKey` and `AuditRequestNonce` is backup-only; its password and dump are protected as secrets. The backup target matches the application target; assert `has_database_privilege` is false for every non-target database after revoking both PUBLIC and direct backup-role CONNECT grants. Known manifest-object ACL drift is transactionally repaired and startup proceeds only after exact re-verification; unknown objects, ownership drift, or unrepaired drift fails unchanged and blocks startup.
- [ ] Auth integration works under the actual restricted runtime role. Runtime can perform only the enumerated auth/tenant/RBAC reads and writes; direct Sequence, student, fee, payment, ledger, receipt, `_prisma_migrations`, `SchemaIndexBuild`, and all migration-control access other than SELECT on `app_schema_capabilities` are denied until an approved feature grants it. Number allocation succeeds only after the DB-001 reservation function is installed and `SequenceService` uses it; prove concurrency, format rollover, settings-race, and transaction rollback invariants.
- [ ] Before cutover, AuditLog has only the current trusted application's required SELECT/INSERT grants and the capability marker is runtime SELECT-only; document/test that this legacy path permits runtime-credential audit forgery. After cutover, actual restricted-role direct AuditLog SELECT and INSERT both fail, as do direct head/key/nonce access; only approved tenant-bound wrappers append/read, and marker access remains SELECT-only. Tests cover marker-absent, no-row, committed-row, and cutover-rollback cases. A barrier test races shared-lock grant sync against exclusive-lock cutover; repeated sync/restart after marker commit never restores direct access.
- [ ] Invalid credentials, role state, target drift, unknown or unrepaired grant drift, and migration failure block API startup without exposing credentials. Known manifest-listed ACL drift may be repaired; startup proceeds only after exact re-verification.
- [ ] Tests cover safe initial provisioning, idempotent repeat, password rotation under the documented maintenance window (including existing-session and reconnect behavior for API, migration, and backup), rotation rollback after bootstrap/migration failure, admin/migration/runtime/backup name and password collisions, privileged pre-existing roles/memberships, exact positive/negative catalog grants, unexpected model/catalog objects, migration failure ordering, and credential redaction. Concurrent bootstrap plus injected failures at each creation/grant step leave no partial privilege state. Native PostgreSQL 17 integration tests exercise real grants and Compose startup ordering. Extension tests cover absent/install, compatible existing installation, and incompatible version/schema/owner refusal. Backup tests prove target mismatch is rejected and second-database connection denied; `pg_dump` runs under the read-only role, output is encrypted with the configured `age` recipient before persistent storage, the recipient identity decrypts it in a disposable restore database, table/sequence writes and application-function calls fail, and a complete snapshot of every financial/audit table matches after restore, including fee demands/items, credits/allocations, invoices/lines, installments, posted adjustments/late fees, audit/signing/nonces, sequence/settings, payment/provider, ledger, refunds, receipts, and reconciliation rows. Fail closed if large objects are added without a reviewed backup policy.
- [ ] Existing-database owner tests separately inject a non-migration owner for a schema, table/partitioned table, view, sequence, enum/domain type, and function/procedure; each is reported and rejected with ownership and row snapshots unchanged.
- [ ] Startup failure tests separately cover provisioning, pre-index migration, grant sync, index runner, post-index migration, final privilege verification, and API health; API and worker remain gated, and recovery succeeds after a retry.
- [ ] Under the actual restricted runtime role, INSERT/UPDATE/DELETE/TRUNCATE attempts fail for every financial/evidence model and `Sequence`; snapshot every protected table before/after the matrix. Confirm no effective rights arrive through PUBLIC, inherited memberships, default ACLs, or function EXECUTE. Financial/domain review approves the operation-level ACL and native database checks; sequence operations preserve the DB-001 numbering invariants.
- [ ] Across final cutover, grant synchronization, repeated restart, and injected failure/rollback, compare complete AuditLog byte snapshots and complete posted-financial snapshots. Successful cutover/reconciliation changes only approved additive audit metadata and grants; failure leaves marker, ACLs, AuditLog rows, and posted financial rows unchanged.
- [ ] Architecture, security/tenant, financial/domain, and QA reviewers approve after implementation.
- [ ] Deployment and database documentation describe the bootstrap credential boundary, role rotation, and existing-database ownership limitations.

## Known risks requiring review

- The ACL synchronizer inventories the exact generated `fee_prevent_identity_reassignment()` routine, tenant-identity triggers, and the audit-head provisioning trigger. It grants the signed audit append, verification, and tenant-scoped read wrappers while retaining legacy table grants before cutover, then applies wrapper-only table ACLs when the marker is committed. The operator cutover transaction revokes the direct audit-table privileges at the same time it inserts the marker. Both paths and restart behavior remain unverified; lifecycle/delete trigger inventory also remains open, and repeated sync must never restore direct AuditLog access after cutover.
- Function-owner roles have no `public` CREATE privilege. DB-001 migrations that transfer wrapper/trigger ownership must use a reviewed temporary CREATE grant/revoke sequence and prove runtime/backup never receive schema CREATE.
- `app_private` extension ownership, schema privileges, function execution grants, and catalog classification must exactly match the approved contract; existing incompatible installations fail closed for a separately reviewed forward operation.
- The numbering reservation and settings-lock functions are now implemented with tenant-bound transaction RPCs and exact runtime EXECUTE grants in the ACL synchronizer. The migration and role/column grants still require PostgreSQL integration, concurrency/rollback exercises, and independent review before number-issuing routes are enabled.
- Provisioning must support fresh databases without accidentally claiming safe automatic ownership adoption for pre-existing databases.
- The current Docker engine is unavailable in this local environment; native PostgreSQL/Compose integration verification must run in CI or another environment with Docker access.
- DB-002 introduces `fee_backup` and streams encrypted artifacts using an `age` recipient, but that does not complete production recovery readiness. Point-in-time recovery, object-storage backups/versioning, recurring restore drills, and incident runbooks required by architecture §55 remain separate gates; production readiness must not be claimed until they pass.
