# Multi-tenant SaaS admin review

> Product direction, core/module ownership, India fee workflows, and the remaining industry-neutral billing checklist are documented in [Generic SaaS Core and Optional Module Boundaries](./generic-platform-and-india-fee-module.md).

**Scope:** review of the current codebase plus the generic platform, branch, access, entitlement, and verified custom-domain changes made in follow-up work. “Existing” means present in source. On 2026-10-07, the staged Neon deployment verified all 62 migrations through `20261007000200_user_email_change_token_index`. The 111-relation tenant preflight passed; all 204 relation indexes were already successful; audit signing-key provisioning completed; and database ACL synchronization completed for 103 public relations and 94 tenant identity guards. The prior organization branding backfill verified 5 rows with 0 mismatches. This verifies database deployment, not production DNS/TLS, complete branch isolation across every route/report/export, billing-provider operation, or a backup restore exercise.

Follow-up implementation note (2026-10-07): tenant provisioning has a guided web review and an idempotency ledger. Tenant users, initial Tenant Admins, and newly created Super Admins use single-use, 48-hour invitation tokens, transactional outbox email, host-bound acceptance pages, password setup, and address verification. Active accounts can request a new sign-in email after re-entering their password; the old email stays active until the new address uses a single-use 30-minute verification link. Both new migrations are applied to Neon. Live SMTP delivery, production browser-host flow, and concurrent provisioning retry proof remain unverified.

Operations/payment follow-up (2026-10-07): production Compose now defaults to one API/web/worker process with smaller service caps, requires commit-SHA GHCR image tags, pulls before deployment, and supports encrypted S3-compatible backup uploads. Application telemetry settings that had no SDK consumer were removed. The tenant fee refund flow calls supported provider adapters and posts local ledger reversals only after an exact provider success response; pending or ambiguous states remain processing and have an audited provider reconciliation form. No production image rollout, external alerting, full refund webhook/polling lifecycle, or backup restore drill has been verified. See the [production deployment and recovery runbook](production-deployment-hardening.md).

## Follow-up: category-aware provisioning and Super Admin navigation (2026-10-12)

### Audit before implementation

- The platform console combined the overview, tenant directory, provisioning, plans, and platform-admin management into one route with in-page sections. This made the main dashboard noisy and weakened direct links/bookmarking.
- Provisioning already had a five-step form, transactional/idempotent API, plan checks, and a single-use Tenant Admin invitation. It lacked category-aware guidance, a workspace-address availability check while typing, and a readable review of category, plan entitlements, and generated address.
- `Tenant.organizationType` is already a text field and public tenant context already reads it. No schema migration is needed for stable category keys or custom labels.

### Implemented

- Added one shared category catalog with stable keys, display labels, descriptions, people/group terminology, and optional modules supported by Wasl today. The examples are guidance for the generic workspace, not separate tenant architectures.
- Added a custom-category option. Its label is stored in the existing `organizationType` text field; it follows generic workspace terminology/module guidance until a matching optional module is built. Known categories keep stable keys. Unknown values resolve to the generic category for navigation while retaining their original display label.
- Added editable slug preview and authenticated availability checking at `GET /platform/tenants/slug-availability`. The provisioning transaction checks uniqueness again, so the live check is only a preview and cannot bypass the server constraint.
- Kept the existing five stages and added category guidance, plan trial/limits/included-module summaries, and an explicit final review of workspace URL and Tenant Admin invitation expiry.

## End-to-end target architecture

1. **Host resolution:** validate `Host` against platform, local wildcard, production wildcard, or a verified custom-domain table. Resolve one tenant before authentication; ignore client-supplied tenant IDs as authority.
2. **Authentication:** tenant-scoped user lookup, verified email/invite, password/MFA policy, short-lived access token, hashed refresh token, and session-version revocation.
3. **Authorization:** permissions from active tenant roles plus explicit branch/organization-unit/resource scopes. Platform permissions remain a separate control plane.
4. **Entitlements:** resolve current immutable plan version, module grants, tenant overrides, usage counters, and lifecycle state once per request/job; deny disabled modules and over-limit operations consistently.
5. **Tenant core:** organization identity, members, roles, branches, departments/groups, settings, branding, domains, assignments, notifications, and audit trail.
6. **Optional modules:** fee collection is a domain module. Its students, fee schedules, demands, payments, and refunds remain tenant-scoped and gain branch ownership only where the business requires it.
7. **Platform billing:** tenant subscription, immutable invoice snapshot, payment attempts/provider events, reconciliation, refunds, tax, credit notes, and audited manual adjustments are separate from tenant-issued invoices and payments.
8. **Persistence:** Neon PostgreSQL remains the database. Prisma is the repository/schema/query layer using the configured PostgreSQL adapter; migrations create composite tenant constraints and the tenant-reference generator updates the fail-closed query manifest. Raw SQL is reserved for reviewed migrations/operations.
9. **Operations:** outbox-driven notifications/billing jobs, idempotent retries, observability, backup/restore, staged migrations, DB least-privilege roles, and tenant-aware support tooling.
