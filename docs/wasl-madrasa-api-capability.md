# Wasl Madrasa mobile app — API capability matrix

Inspected the current Wasl API controllers, shared validation schemas, Prisma
schema, and tenant/auth middleware. The mobile client in `apps/mobile` uses the
existing versioned API (`/api/v1`) and does not access Neon directly.

| Area | Existing API contract | Mobile integration |
| --- | --- | --- |
| Tenant resolution and branding | `GET /tenant-context` resolves the request hostname and returns active tenant branding, category, enabled modules, and configured timezone. | Workspace URL is resolved before login; returned tenant name, logo, colors, and timezone brand the app and format transaction dates. |
| Sign-in and session | `POST /auth/login` accepts email/password on a resolved tenant hostname; `POST /auth/refresh`, `POST /auth/logout`, `GET /auth/me`; reset request at `POST /auth/forgot-password`. Access token is returned in JSON; refresh token is an HttpOnly cookie. | Role choice is presented on login; actual roles are checked in the returned session. Refresh cookie is kept in platform secure storage by the native client and submitted to the existing refresh/logout contract. |
| Student / parent overview | `GET /portal/dashboard` returns only linked student IDs, names, admission numbers and statuses, fee demands, payment history, receipts, and online payment methods. `GET /portal/receipts/:id` checks that the receipt belongs to a linked student. | Home, fee balance/history, and receipt details use these scoped responses. Multi-student guardian accounts can select only returned profiles. |
| Fee detail | `GET /payments/students/:studentId/open-items` checks linked-student access for portal roles and returns outstanding fee items/responsibilities. | Student/parent fee lists and online order selections use server-calculated outstanding items. |
| Online payment | `POST /gateways/orders` creates a tenant-configured order; `GET /gateways/orders/:id` returns that order. Existing web checkout supports `REDIRECT`, `FORM_POST`, `RAZORPAY`, and `CASHFREE` responses. | App launches supported provider checkout modes and polls the order endpoint. The client trusts only the backend order state. Test `MOCK` checkout is never presented as payment success. |
| Staff student lookup | `GET /students?search=...` and `GET /students/:id` require student-read permission and the API applies staff branch scope. `GET /academic-units` can resolve the primary academic unit for staff permitted to read students. | Staff search and student detail are permission-gated and use scoped API results. |
| Staff fee collection | `GET /payment-methods`, `GET /payments/students/:studentId/open-items`, and `POST /payments/manual`. The collection API validates method, outstanding amount, partial-payment policy, payer responsibility, idempotency key, collector identity, and atomically issues a receipt. | Staff fee collection submits an idempotent request and displays the API's receipt or pending approval result. |
| Staff dashboard | `GET /organization/dashboard` returns organization/branch-scoped workspace counts; `GET /payments` returns permitted payment activity. | Shows the available scoped student count and recent payments where permissions allow. The current dashboard does not return attendance or pending-fee totals. |
| Tenant admin | Existing `students`, `access`, `academic-units`, fee, payment-method, and report APIs enforce their own permissions. | Admin/staff navigation is driven by returned permission keys. The mobile app focuses on student lookup and collection; full tenant setup and role configuration remain in the existing Wasl web console. |

## Backend gaps before full Madrasa feature parity

1. **Attendance is absent.** No attendance model, migration, controller, or API route exists. The smallest compatible backend addition is a tenant-owned attendance session/record model plus scoped routes to list a student's own/linked children's records, list class/group rosters, create bulk attendance with an idempotency key, and correct existing records under a distinct permission. Every query/write must bind to the authenticated tenant and enforce staff assignment scope. This app leaves attendance unavailable until those contracts exist.
2. **Portal profile is intentionally narrow.** The portal dashboard currently returns the student's name, admission number, and status only; it does not return photo, class/unit label, batch/division, or authorised guardian/contact fields. Add a portal-scoped profile endpoint (or extend the portal dashboard) that resolves only linked student IDs and returns approved fields plus an academic-unit display label. The mobile profile screen displays only fields the current API provides.
3. **Online checkout capability discovery is limited.** The portal dashboard returns online payment method ID/name/kind but not safe provider checkout capability metadata. The app can create an order and handle the existing checkout response modes. For preflight display of supported methods without creating an order, add a portal-scoped read endpoint that returns the active online methods and safe provider/mode compatibility. Never return provider secrets.
4. **Notifications are not a student/parent inbox.** Current notification APIs expose templates/history to tenant settings readers, not a linked-student notification feed. The app therefore does not invent recent notifications.
5. **Receipt files are not available.** Existing receipt routes return authorised receipt/payment data, but there is no PDF or download endpoint. The app shows receipt details only; downloadable or shareable receipt files require a tenant-scoped artifact route.

No route definitions, authorization rules, or database schema were changed for this mobile client. The existing tenant-context response is extended with configured timezone and organisation-category display fields.
